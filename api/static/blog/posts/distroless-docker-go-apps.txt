16:Te09,<p>When building Docker images for Go applications, developers historically defaulted to Alpine Linux. Alpine is small, fast, and familiar. However, bundling a full Linux distribution—even a lightweight one—inside a container designed to run a statically compiled binary introduces unnecessary risks and bloat.</p>
<p>We migrated the entire MetroMind microservice architecture from Alpine-based images to Google's Distroless (gcr.io/distroless/static) and FROM scratch containers. This single architectural decision shrank our image sizes from ~300MB to under 10MB and eliminated entire classes of vulnerabilities.</p>
<h2 id="the-alpine-tax"><a href="#the-alpine-tax">The Alpine Tax</a></h2>
<p>A standard Go Dockerfile usually looks like this:</p>
<p>`dockerfile
FROM golang:1.21 AS builder
WORKDIR /src
COPY . .
RUN go build -o myapp main.go</p>
<p>FROM alpine:latest
WORKDIR /app
COPY --from=builder /src/myapp .
CMD ["./myapp"]
`</p>
<p>While lpine:latest adds only ~5MB, it ships with a package manager (pk), a shell (/bin/sh), and standard GNU utilities. If an attacker achieves remote code execution (RCE) in your application, they land in an environment equipped with the tools necessary to download payloads, map the network, and pivot.</p>
<p>Furthermore, security scanners regularly flag Alpine base images for CVEs in standard libraries. Managing these OS-level vulnerabilities wastes engineering time when the application itself does not require an OS userland.</p>
<h2 id="moving-to-distroless"><a href="#moving-to-distroless">Moving to Distroless</a></h2>
<p>Go binaries compile statically. They contain their own runtime and do not require external dependencies like libc unless you specifically link C libraries using CGO.</p>
<p>By disabling CGO during the build phase, we generate a standalone binary that runs directly on the Linux kernel without an OS abstraction layer.</p>
<p>`dockerfile
FROM golang:1.21 AS builder
WORKDIR /src
COPY . .</p>
<h1 id="disable-cgo-for-a-fully-static-binary"><a href="#disable-cgo-for-a-fully-static-binary">Disable CGO for a fully static binary</a></h1>
<p>RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -ldflags="-w -s" -o myapp main.go</p>
<h1 id="use-a-distroless-base"><a href="#use-a-distroless-base">Use a distroless base</a></h1>
<p>FROM gcr.io/distroless/static-debian12:latest
COPY --from=builder /src/myapp /
CMD ["/myapp"]
`</p>
<p>The distroless image contains only the absolute minimum required to run the binary: CA certificates for HTTPS requests, time zone data, and a non-root user. It lacks a shell. It lacks a package manager. If an attacker exploits the application, they cannot easily execute secondary commands because /bin/sh does not exist.</p>
<h2 id="the-from-scratch-alternative"><a href="#the-from-scratch-alternative">The FROM scratch Alternative</a></h2>
<p>For microservices that do not require outbound HTTPS requests (which require CA certificates) or timezone handling, we build directly FROM scratch.</p>
<p><code>dockerfile FROM scratch COPY --from=builder /src/myapp /myapp ENTRYPOINT ["/myapp"] </code></p>
<p>FROM scratch is an empty container. The final image size matches the exact byte size of the Go binary.</p>
<p>Migrating to these ultra-minimal containers forced us to improve our observability stack. Because we can no longer docker exec -it <container> /bin/sh to debug failing pods, we must rely entirely on structured logging, metric endpoints, and distributed tracing. Removing the crutch of local container debugging ultimately produced more resilient, observable
